# ModelSwitch 可用性评估报告

> **版本**: v1.0 · **日期**: 2026-07-03 · **评估对象**: ModelSwitch 桌面端 + CLI（Rust LLM 智能网关）
> **评估方法**: Nielsen 启发式评估 + LLM 网关行业维度 + 用户路径走查 + 代码层证据
> **评估目的**: 为一人公司提供可操作的优先级排序，指导下一个冲刺期的开发投入

---

## 0 执行摘要（TL;DR）

ModelSwitch 当前可用性成熟度处于 **3/5（基本可用）**：功能完整、核心链路畅通，但存在若干**高 severity 的"功能欺骗"问题**（最典型为 Playground 的假 Stream 开关、未接入请求管道的 GuardrailsChecker）与**无障碍/引导空白**。产品后端能力（路由、熔断、虚拟密钥、审计链）已具备生产骨架，但**前端暴露面与文档引导未能匹配后端复杂度**。

**下个冲刺期 Top 3 修复**：
1. P0：消除"功能欺骗"——Playground Stream 开关、GuardrailsChecker 未接线、Web 控制台 fallback 返回 HTML 200
2. P0：补齐首次启动引导与空状态指引（避免新用户面对空白仪表盘）
3. P1：补齐 ARIA live region 与键盘可访问的渠道优先级排序（拖拽仅鼠标可用）

完整量化评分见 [§5.2](#52-量化评分)。

## 1 评估框架

### 1.1 Nielsen 十大可用性原则（适配 LLM 网关管理控制台）

| # | 原则 | 在 LLM 网关场景下的具体含义 |
|---|------|------------------------------|
| H1 | 系统状态可见性 | 请求转发、熔断、降级过程中用户能否实时看到渠道状态、健康度、错误码；Toast 是否被屏幕阅读器接收 |
| H2 | 系统与现实世界匹配 | "渠道"、"虚拟密钥"、"熔断"、"模型降级"、"Token 桶"等术语是否贴合开发者心智；命名是否一致 |
| H3 | 用户控制与自由 | 误删渠道、错误导入备份、错误停用密钥后能否撤销；危险操作是否有确认 |
| H4 | 一致性与标准 | 17 个面板的错误处理、表单校验、分页/加载更多、批量操作模式是否统一 |
| H5 | 防错 | 破坏性操作（备份还原、密钥删除、渠道停用）是否防误触；TOML-only 字段修改后是否会因 reload 范围不匹配产生错觉 |
| H6 | 识别而非回忆 | Cmd+1..9 快捷键、5 种路由策略、fallback 链层级是否在 UI 中可见；技术概念是否有 tooltip 解释 |
| H7 | 使用的灵活性与效率 | 键盘导航、批量操作、模板复制、命令面板等加速器是否覆盖资深用户的高频路径 |
| H8 | 美学与极简设计 | 信息密度是否合理；20+ 监控面板是否有视觉层次；成本仪表盘是否能一屏给出关键信号 |
| H9 | 帮助用户识别、诊断、恢复错误 | 错误提示是否给出根因与修复路径（不只是 toast "失败"）；429/熔断/限额触达后的指引是否明确 |
| H10 | 帮助与文档 | 是否有首次引导、空状态指引、术语解释、in-app help；CLI 命令是否完备 |

## 2 用户操作路径分析

### 2.1 路径 A：首次启动 → 登录 → 添加渠道 → 测试连通性 → 创建虚拟密钥 → 使用 Playground

| 步骤 | 节点 | 摩擦等级 | 具体问题 |
|------|------|----------|----------|
| 1 | 启动桌面端 | 🟢 | 安装顺畅，系统托盘常驻符合预期 |
| 2 | 首次进入登录页 | 🔴 | 无 onboarding 向导；admin token 与 portal 双轨登录无解释；新用户不知道 token 从哪来 |
| 3 | 输入 admin token 进入主界面 | 🟡 | dashboard 为空时空状态无指引（"去添加第一个渠道"按钮缺失） |
| 4 | 导航到 Channels 面板 | 🟢 | 侧边栏分组合理，5 组 17 面板结构清晰 |
| 5 | 添加第一个渠道 | 🟡 | 表单字段较多但缺乏分段；无模型别名/分组/pricing 的内联解释；保存后无"测试连通性"快捷入口引导 |
| 6 | 测试渠道连通性 | 🟢 | 测试按钮存在且响应快 |
| 7 | 创建虚拟密钥 | 🟡 | 限额字段（RPM/TPM/日/月预算）对非运维背景用户无解释；密钥创建成功后**明文 toast 展示**，用户若错过则永久丢失 |
| 8 | 在 Playground 试用 | 🔴 | **Stream 开关为假**（`Playground.tsx:165` 硬编码 `stream: false`）；UI 承诺与后端行为不一致，违反信任契约 |

**路径 A 摩擦总结**：3 绿 / 3 黄 / 2 红。最大障碍集中在"第一次看到主界面"与"Playground 试用"两个节点——前者没有指引，后者存在功能欺骗。

### 2.2 路径 B：日常运维 —— 查看仪表盘 → 检查日志 → 处理渠道故障

| 步骤 | 节点 | 摩擦等级 | 具体问题 |
|------|------|----------|----------|
| 1 | 打开 Dashboard | 🟡 | 部分面板 5 秒轮询造成视觉抖动与性能开销；无聚合"健康摘要"卡片 |
| 2 | 查看请求日志 | 🟡 | 日志面板存在，但缺乏按错误码/渠道/模型的快速过滤；高频日志下滚动性能未优化 |
| 3 | 查看审计日志 | 🔴 | 环形缓冲仅 1000 条，**无分页、无加载更多、无过滤**；超过 1000 条后旧记录直接丢失，无法审计追溯 |
| 4 | 处理熔断渠道 | 🟡 | 渠道熔断状态可见，但冷却时长、剩余时间、解除条件未在 UI 直观展示 |
| 5 | 手动重启渠道 | 🟢 | 启用/停用开关即时生效 |
| 6 | 查看成本趋势 | 🟢 | CostDashboard 与 Reports 面板覆盖到位 |

**路径 B 摩擦总结**：2 绿 / 3 黄 / 1 红。审计日志的硬性上限是合规性缺陷；轮询策略和熔断状态可视化是体验欠账。

### 2.3 路径 C：高级配置 —— 设置路由策略 → 配置模型降级 → 预算管理

| 步骤 | 节点 | 摩擦等级 | 具体问题 |
|------|------|----------|----------|
| 1 | 在 UI 选择路由策略 | 🟡 | 5 种策略（weighted/latency/least_busy/usage/lowest_cost）可切换，但无 tooltip 解释差异；切换后影响范围无预览 |
| 2 | 配置模型降级链 | 🔴 | **ModelRoutingPanel 为只读**——别名、fallback、pricing 仅可查看，编辑必须改 TOML；违反"所见即所改"预期 |
| 3 | 通过 TOML 编辑高级字段 | 🔴 | `reload_config` **仅重载 channels**，不重载完整 gateway 块；用户修改 model_fallbacks/model_aliases 后调用 reload 会被静默忽略，产生"我改了但没生效"的错觉 |
| 4 | 设置预算与预算预警 | 🟡 | 虚拟密钥日/月预算可配，但预警阈值、超额行为、Notification 联动说明分散 |
| 5 | 配置通知渠道 | 🟢 | webhook/Bark/SMTP 三通道完整 |
| 6 | 启用消毒器/护栏 | 🔴 | **GuardrailsChecker 在 state 中构造（`dispatch.rs:1511`，测试代码）但实际请求管道未调用 `check_request`**；UI 显示护栏已启用但请求不被检查——这是安全功能欺骗 |
| 7 | MCP 工具网关配置 | 🟡 | auto-inject 模式会将流式请求**强制降级为非流式**，UI 无显著警告 |

**路径 C 摩擦总结**：1 绿 / 2 黄 / 4 红。这是**最深层的可用性问题集中区**——核心高级能力（降级、护栏、热重载）存在"UI/TOML 承诺与运行时行为不一致"的系统性风险。

## 3 用户分层评估

### 3.1 新用户（首次部署网关的管理员）

| 指标 | 估计值 | 依据 |
|------|--------|------|
| 任务完成率（完成"添加渠道+创建密钥+Playground 验证"） | **约 55-65%** | 无引导、空状态缺位、Playground 假 Stream 开关易让用户误判"产品坏了" |
| 完成关键链路的耗时 | **15-25 分钟** | 路径 A 步骤 2/3/7/8 均有摩擦；熟悉 LLM 网关概念的用户偏低，纯开发者偏高 |
| 首次错误率（误操作、字段填错、token 丢失） | **约 30%** | 虚拟密钥明文 toast 一次性展示、双 auth 模式混淆、TOML-only 字段无提示 |

**主要障碍**：缺少首次引导、术语解释、空状态指引、token 一次性展示的兜底。

### 3.2 资深用户（日常运维渠道/密钥/监控的工程师）

| 指标 | 估计值 | 依据 |
|------|--------|------|
| 日常任务完成率（查日志、启停渠道、调预算） | **约 85-90%** | 核心面板功能完整，键盘快捷键可用（虽未文档化） |
| 单次运维耗时（处理一个熔断渠道） | **2-4 分钟** | 渠道状态、日志、成本面板可用；冷却时长未可视化导致判断稍慢 |
| 高级配置错误率（路由/降级/护栏） | **约 40%** | TOML-only 字段 + reload_config 范围错位 + Guardrails 未接线，三者叠加极易配置出"看起来对、实际不生效"的状态 |

**主要障碍**：高级配置的"行为可预期性"低；审计日志截断影响追溯；轮询抖动。

### 3.3 特殊需求用户（仅键盘、屏幕阅读器、需要 reduced-motion）

| 指标 | 估计值 | 依据 |
|------|--------|------|
| 任务完成率（仅键盘完成核心流程） | **约 30-40%** | 渠道优先级卡片**仅鼠标拖拽**；模态框/面板切换无焦点管理；Cmd+1..9 未文档化 |
| 屏幕阅读器可用性 | **极低** | Toast 无 ARIA live region；状态指示用颜色单通道表达；20+ 面板仅约 39 处 ARIA 引用 |
| reduced-motion 适配 | **无** | 全应用无 `prefers-reduced-motion` 分支 |

**主要障碍**：交互组件普遍未遵循 WAI-ARIA 模式（tabs、dialog、listbox），无障碍基本缺位。

## 4 可用性短板识别（按类别）

### 4.1 信息架构（IA）

- **IA-1**：17 面板分 5 组结构合理，但 Monitoring 组下塞了 7 个面板（Cost/Quota/Logs/Metrics/Audit/Model Registry/Reports），**组内密度过高**，新用户难以定位。
- **IA-2**：高级配置概念（model_groups、model_pricing、group_ratios、context_window_fallbacks）**在 UI 中完全不可见**，造成"产品能做什么"的认知断层。
- **IA-3**：双 auth（admin/portal）模式在登录页无说明，用户不知道该用哪个入口。
- **IA-4**：CLI 命令极简（serve/init/validate/channels/status/stop），**无法覆盖管理操作**，CLI 与桌面端的职责边界未传达。

### 4.2 交互逻辑（与用户心智模型的偏差）

- **IL-1**：**Playground Stream 开关为假**（代码证据：`src/components/playground/Playground.tsx:165`）。用户切换开关后行为不变——这是直接的功能欺骗。
- **IL-2**：**GuardrailsChecker 已实现 `check_request` 但请求管道未调用**（代码证据：`src-tauri/src/proxy/dispatch.rs:1511` 仅在测试中构造；`check_request` 在 `guardrails.rs:109` 定义但无生产调用方）。UI 显示护栏启用即承诺安全检查，实际不生效。
- **IL-3**：**`reload_config` 仅重载 channels，不重载完整 gateway 块**——用户通过 TOML 改 model_fallbacks/model_aliases 后调用 reload，预期全量生效，实际部分生效，产生难以排查的"半生效"状态。
- **IL-4**：**Web 控制台 fallback 对未匹配 API 路径返回 index.html（HTTP 200）**——CLI 调用拼写错误的端点会收到 HTML 200 而非 JSON 404，违反 REST 预期。
- **IL-5**：**ModelRoutingPanel 只读**——用户在 UI 看到 fallback/pricing，自然预期可编辑，实际只能改 TOML。
- **IL-6**：**MCP auto-inject 将流式降级为非流式**——对依赖流式的客户端是行为突变，UI 缺少显著警告。
- **IL-7**：模型 fallback 不更新 body 的 `model` 字段（除非渠道配 model_mapping），下游观察到的模型名可能与实际路由不一致。

### 4.3 反馈机制

- **FB-1**：Toast 组件**无 ARIA live region**，屏幕阅读器用户感知不到通知。
- **FB-2**：错误处理跨面板**不一致**——有的弹 toast、有的内联、有的静默；无统一错误边界策略。
- **FB-3**：5 秒高频轮询在部分面板造成**视觉抖动与 refetch 疲劳**；未采用 TanStack Query 的 `staleTime`/`refetchInterval` 分级策略。
- **FB-4**：**虚拟密钥创建成功后明文 toast 单次展示**，错过即丢失，无"再次显示"或"复制到剪贴板"兜底。
- **FB-5**：熔断渠道的**冷却剩余时间、解除条件未可视化**。
- **FB-6**：表单校验**无 schema 化（无 Zod）**，每个面板各写一套，提示时机和质量不统一。

### 4.4 无障碍支持（WCAG 失败项）

| WCAG 条款 | 失败点 |
|-----------|--------|
| 1.1.1 非文本内容 | 部分状态指示仅用颜色，无文本/图标冗余 |
| 1.3.1 信息与关系 | 自定义侧边栏未用 WAI-ARIA tabs 模式，语义缺失 |
| 1.4.3 对比度（最低） | 部分 status badge 颜色对比未验证 |
| 2.1.1 键盘可访问 | 渠道优先级拖拽**仅鼠标可用**；模态框无焦点陷阱 |
| 2.4.1 跳过块 | 无 skip-to-content 链接 |
| 2.4.3 焦点顺序 | 面板切换、模态打开/关闭无焦点管理 |
| 3.2.1 可预测 | Cmd+1..9 快捷键存在但**未在 UI 提示** |
| 3.3.1 错误识别 | 表单错误提示不统一 |
| 4.1.2 名称/角色/值 | 20+ 面板仅约 39 处 ARIA 引用，覆盖率低 |
| 4.1.3 状态消息 | Toast 无 `role="status"` / `aria-live` |

### 4.5 文档与引导

- **DOC-1**：**无首次启动向导**。
- **DOC-2**：**无空状态指引**（无渠道时 dashboard 应给出"添加第一个渠道"CTA）。
- **DOC-3**：**无 in-app help / 术语表 / tooltip**（5 种路由策略、fallback 链、熔断、Token 桶均无解释）。
- **DOC-4**：Cmd+1..9 快捷键**未在任何 UI 暴露**。
- **DOC-5**：TOML-only 字段（model_fallbacks、model_groups、group_ratios、context_window_fallbacks、rate_limit_algorithm、redis、http_pool_size 等）**在 UI 无任何提示"此功能需通过 TOML 配置"**。

## 5 结构化评估报告

### 5.1 问题清单

> 严重等级：**高**（影响信任/安全/数据完整性） · **中**（影响效率/可发现性） · **低**（体验打磨）
> 优先级：**P0**（下个冲刺必修） · **P1**（下个冲刺尽量） · **P2**（ backlog 排期）

| # | 问题 | 严重等级 | 影响范围 | 修复建议 | 优先级 |
|----|------|----------|----------|----------|--------|
| Q1 | Playground Stream 开关硬编码为 false，UI 承诺与行为不符 | 高 | 所有 Playground 用户 | 将 `stream` 字段绑定到 toggle 状态 | P0 |
| Q2 | GuardrailsChecker.check_request 未接入请求管道，UI 显示启用但无实际检查 | 高 | 所有依赖护栏的安全场景 | 在 dispatch 管道中调用 `state.guardrails.check_request(&body)` 并处理 `GuardrailAction` | P0 |
| Q3 | `reload_config` 仅重载 channels，不重载 gateway 块，产生"半生效"状态 | 高 | 所有 TOML 运维用户 | 扩展 reload 范围或显式标注"仅 channels 字段热重载，其余需重启" | P0 |
| Q4 | Web 控制台 fallback 对未匹配 API 返回 HTML 200 而非 JSON 404 | 高 | CLI/程序化调用方 | 仅对非 `/` 路径的 API 前缀返回 JSON 404，HTML fallback 限制到静态资源 | P0 |
| Q5 | 无首次启动向导 + 无空状态指引 | 高 | 所有新用户 | dashboard 空状态加"添加第一个渠道"CTA；首次进入触发 3 步引导 | P0 |
| Q6 | 审计日志环形缓冲 1000 条硬上限，无分页/过滤，超限丢失 | 高 | 合规/追溯场景 | 增加基于 NDJSON 文件的分页加载与按时间/操作类型过滤 | P0 |
| Q7 | 渠道优先级卡片仅鼠标拖拽，键盘完全不可用 | 高 | 键盘用户/无障碍 | 提供"上移/下移"按钮 + ArrowUp/Down 键盘等效 | P0 |
| Q8 | 虚拟密钥创建后明文 toast 单次展示，错过即丢失 | 高 | 所有创建密钥的用户 | 改为模态展示 + "复制" + "我已保存" 确认；提供一次性再显示入口 | P0 |
| Q9 | Toast 无 ARIA live region，屏幕阅读器收不到通知 | 中 | 视障用户 | 给 Toast 容器加 `role="status" aria-live="polite"` | P1 |

### 5.3 定性结论

#### 当前可用性成熟度

**3 / 5 —— 基本可用**

产品已度过"概念原型（1）"与"功能完整但粗糙（2）"阶段，核心后端能力（路由、熔断、虚拟密钥、审计链、MCP 网关）具备生产骨架，主要面板可用。但距离"体验流畅（4）"仍有系统性欠账，主要卡在**"UI/运行时行为一致性"** 与 **"无障碍/引导空白"** 两类问题上。

#### Top 5 优势

1. **后端能力深度**：5 路由策略 + 双层熔断 + fallback 链 + LRU 缓存 + 脱敏器，能力栈覆盖 LLM 网关核心场景。
2. **虚拟密钥体系**：日/月预算 + RPM/TPM + 哈希存储 + RBAC，安全模型完整。
3. **审计链设计**：SHA-256 哈希链 + NDJSON 持久化，合规骨架扎实（前提是解决 1000 条截断）。
4. **成本可视化**：CostDashboard + Reports + Quota 三视图，成本可见性是同类竞品的差异化卖点。
5. **热重载理念**：渠道/缓存/路由/护栏/通知热重载，运维心智成本低（待扩大覆盖范围）。

#### Top 5 关键短板

1. **"功能欺骗"集群**（Q1 Stream 假开关 + Q2 Guardrails 未接线 + Q3 reload 半生效 + Q4 API 返回 HTML 200）——直接侵蚀用户信任，且每一条都影响安全或正确性。
2. **首次体验空白**（Q5 无引导 + DOC-1/2/3/4/5）——新用户流失漏斗的最大出口。
3. **无障碍系统性缺位**（Q7/Q9/Q17/Q18/Q21 + reduced-motion 缺失）——不仅失去特殊需求用户，也违反多地区合规要求。
4. **审计日志硬截断**（Q6）——合规性硬伤，对 企业/团队 卖点是阻断性缺陷。
5. **TOML 与 UI 的"双世界"断层**（Q10/Q23 + IA-2）——大量高级能力 UI 不可见，与"零 CLI 门槛"的产品定位矛盾。

#### 推荐下个冲刺期优先级

**P0（必修，2-3 个工作日可完成）**：
1. 修复 Playground Stream 开关（Q1）——1 行代码改动。

5. 虚拟密钥创建改模态 + 复制 + 确认（Q8）——半天。
6. 审计日志分页加载（Q6）——1 天。

**P1（尽量排入，1-2 周）**：
- 渠道优先级键盘可访问（Q7）+ skip-to-content（Q17）+ Toast ARIA（Q9）——无障碍三件套。
