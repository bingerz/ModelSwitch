### 2.3 补充评估（可用性报告未覆盖维度）

#### 2.3.1 新手引导 / Onboarding

**评分：3 / 10**

- 有渠道空状态 CTA（P1 修复成果），但**无完整首次启动向导**——新用户首次进入仍面对登录页 token 来源不明的问题。
- 登录页仍无双 auth 模式（admin/portal）解释。
- 无 in-app help / 术语表 / tooltip 库（`grep` 仅找到 4 个文件含 "Tooltip"，且为图表专用，不是概念解释）。
- **CLI 命令仅 5 条**（serve/init/validate/channels/status/stop），无法覆盖管理操作，CLI 与桌面端职责边界未传达。

#### 2.3.2 错误恢复体验

**评分：5 / 10**

- HTTP 错误码文档完整（`troubleshooting.md` 列出 400/401/402/403/429/502/503/504 + 错误信息表），但**in-app 无根因指引**——429 触发后用户看到的只是 toast，无"该怎么做"链接。
- 备份还原有 `restore.sh` 脚本，但**无 UI 二次确认/diff 预览**（Q16 仍未修）。
- 渠道熔断的冷却剩余时间仍未可视化（Q25 未修），用户不知道还要等多久。

#### 2.3.3 性能感知

**评分：6 / 10**

- TanStack Query 全局 `retry: 1`，staleTime 5s（`App.tsx:76-78`）。

#### 2.3.4 移动端适配

## 3 运维成本详细评估（6.8 / 10）

### 3.1 部署复杂度

**评分：7 / 10**

| 方案 | 步骤数 | 首次可用耗时（估算） | 评价 |
|------|--------|---------------------|------|
| Docker Compose | 4 步（mkdir + .env + cp config + `up -d`） | 10-15 分钟 | 文档完整，资源限制内置（1 CPU/512MB），健康检查就绪 |
| systemd | 5 步脚本（`install-systemd.sh` 自动化）+ 编译二进制 | 20-30 分钟（含 `cargo build --release`） | 安全加固到位：`NoNewPrivileges`、`ProtectSystem=strict`、`PrivateTmp`、`ProtectKernel*` |
| Tauri 桌面端 | 一键安装 | 5 分钟 | 适合开发者个人使用；**不适合 headless 工控机** |

- **Tauri 桌面端对 OPC 场景是负资产**：工控机普遍 headless Linux，桌面端依赖 GUI。生产形态应锁定 CLI + systemd（REQ-10 已明确）。
- Docker 与 systemd 双方案的文档（`deployment-guide.md`）质量高，步骤清晰。

### 3.2 日常运维

**评分：7 / 10**

| 操作 | 流程 | 评价 |
|------|------|------|
| 配置变更 | 改 TOML → `POST /api/config/reload`；**仅 channels 字段热重载**，其余需重启（现已明确标注） | 可用，但热重载范围窄 |
| 日志管理 | NDJSON 自动轮转 5 文件（约 500MB）+ `archive-logs.sh` gzip 归档 + cron 定时（每日 2AM） | 完善，180 天保留满足多数合规 |
| 备份恢复 | `backup.sh` + cron + `restore.sh`；备份内容含 6 类文件 | 完善，但**无增量备份**，每次全量 |
| 升级流程 | Docker: `compose up -d --build`；systemd: 重编译 + cp + restart | systemd 升级路径较重，无 deb/rpm 包 |

- 配置热重载现已在 API 响应中明示范围（`reloaded`/`not_reloaded`），消除了"半生效"陷阱——这是一个值得肯定的修复。
- 日志归档脚本的保留策略可配置（`LOG_RETENTION_DAYS=30` / `ARCHIVE_RETENTION_DAYS=180`），符合 IEC 62443 与等保审计留存要求。

### 3.3 监控告警

**评分：6 / 10**

- **Prometheus 指标**：`metrics.rs` 暴露 13+ 指标，覆盖请求量、延迟直方图、Token 用量、成本、缓存命中率、熔断状态、重试次数、TTFT——**指标覆盖度高**。
- **Grafana 仪表盘**：`deploy/grafana/modelswitch-dashboard.json` 开箱即用。
- **告警规则**：`deploy/prometheus/alerts.yml` 预置 3 条（HighErrorRate >5%、HighLatencyP99 >2s、ChannelCircuitOpen）——**数量偏少**，缺少磁盘空间、内存、上游 API 不可达、预算即将耗尽等规则。
- **告警通知通道**：Webhook + Bark + SMTP 三通道，但**无微信/钉钉/企业微信**（REQ-17 明确要求）。

### 3.4 故障恢复

**评分：7 / 10**

- **RTO/RPO 明确**：≤ 30 分钟 / ≤ 10 分钟（`disaster-recovery.md`）。
- **5 类故障场景**有详细恢复步骤：进程崩溃、硬盘故障、网络中断、数据损坏、主机失效。
- 进程崩溃由 systemd `Restart=always` 自动恢复（< 1 分钟）。
- **数据恢复流程未经实际演练记录**——文档写了流程但无"最近一次成功恢复演练"的记录或自动化测试。
- **审计日志哈希链**（SHA-256 `prev_hash`）提供篡改检测，恢复后可校验。

### 3.5 资源消耗

**评分：5 / 10**

| 指标 | PRD 目标 | 实际配置 | 差距 |
|------|----------|----------|------|
| 内存 | NFR-05 **< 50 MB** | Docker 限制 **512 MB**（reservations 128 MB） | **10 倍超标**——PRD 目标不现实或未优化 |
| 磁盘 | 未定义 | 日志约 500MB（5 轮转文件）+ 归档 gzip | 可控 |
| CPU | 未定义 | Docker 限制 1.0 CPU（reservations 0.25） | 合理 |

- **内存 512MB vs 目标 50MB 是重大差距**。Rust + Axum + Tokio + reqwest 连接池 + Prometheus 指标 + 审计哈希链的实际 RSS 远超 50MB。PRD 的 NFR-05 目标需修正——**建议改为 < 200MB（生产负载）**，与 OPC 调研报告的"工控机 4 核 8GB 可承载 ≥ 3 租户"约束对齐。
- 无内存指标暴露（Prometheus 未导出 `process_resident_memory_bytes`）——运维无法基于内存告警。

### 3.6 运维维度打分

7 + 7 + 6 + 7 + 5 = 32 / 5 = 6.4，加权修正后 **6.8 / 10**（部署文档质量与 systemd 安全加固拉高分数）。

## 4 OPC 合规适配性详细评估（3.0 / 10）

> **前提**：ModelSwitch 当前是 LLM 网关，OPC UA 协议栈完全缺失。本评估基于"LLM 网关侧已有能力对 OPC 合规的贡献度"+"向 OPC 延伸的预备度"。

### 4.1 IEC 62443 适配（SL2 级别）

**评分：2.5 / 10**

| IEC 62443-3-3 FR | 当前满足度 | 证据 / 差距 |
|-------------------|-----------|------------|
| FR1 标识与认证控制 | **40%** | RBAC + 虚拟密钥 + LDAP/OIDC 已实现；但**无设备认证**（X.509 证书认证 OPC UA 设备不存在） |
| FR2 使用控制 | **30%** | RBAC 角色模型在位；**无强制访问控制策略引擎**、无会话超时配置 |
| FR3 数据完整性 | **50%** | 审计日志 SHA-256 哈希链（`audit.rs:41` `prev_hash`）+ NDJSON 追加写入；**但 1000 条环形缓冲超限后旧记录被丢弃**，违反完整性留存要求 |
| FR4 数据机密性 | **40%** | rustls TLS 热重载已实现（`server/tls.rs`）；**但无 Zone & Conduit 分区**——ModelSwitch 作为单进程无法表达 IEC 62443 的分区模型 |
| FR5 受限数据流 | **0%** | 无网络分区能力；无 OPC UA Security Policy 实现 |
| FR6 随时审计 | **35%** | 审计日志 + 哈希链 + 180 天归档；但**无工业字段**（操作人/设备/点位/指令类型），缺 REQ-15 要求的扩展 |
| FR7 资源可用性 | **20%** | 熔断 + 限流 + 预算控制；**无 DoS 防护、无冗余部署模式** |

**SL2 级综合满足度约 25-30%**。主要差距：无 Zone & Conduit、无设备认证、审计字段不足、无数据流管控。

### 4.2 等保 2.0（工控扩展）适配

**评分：3.5 / 10**

| 等保要求 | 当前满足度 | 证据 / 差距 |
|---------|-----------|------------|
| 安全审计 | **50%** | 审计链 + 180 天归档 + 哈希防篡改；但 1000 条缓冲是硬伤，UI 分页仅是切片展示而非持久化查询 |
| 访问控制 | **45%** | RBAC + 虚拟密钥 + group 字段（可映射租户）；但**无等保要求的三权分立**（系统管理员/安全管理员/审计管理员） |
| 通信完整性 | **30%** | TLS 在位；**无报文完整性校验**（OPC UA 的消息签名不存在） |
| 入侵防范 | **15%** | URL SSRF 校验（`commit eac1c33`）、CRLF 注入过滤、消毒器；**无 IDS/IPS 集成、无流量异常检测** |
| 安全管理中心 | **10%** | 有管理 API + UI；**无集中安全管理平台能力**，无多设备统一策略下发 |

### 4.3 数据安全法适配

**评分：2.5 / 10**

| 要求 | 当前满足度 | 证据 / 差距 |
|------|-----------|------------|
| 数据分类分级 | **0%** | 无元数据字段标注数据级别（一般/重要/敏感）；`grep "data_class\|classification"` 零命中 |
| 数据生命周期管理 | **10%** | 审计日志有保留策略；**业务数据（密钥/配额/日志）无生命周期删除策略**，无"数据到期自动销毁" |
| 数据出境管控 | **20%** | 本地部署架构支持数据不出境；**但 LLM 请求 inherently 将数据发往境外 API**（OpenAI/Anthropic），无出境标记/拦截/脱敏前置 |
| 多租户数据隔离 | **40%** | `virtual_key.group` 字段可映射 tenant；**但隔离仅停留在路由层，未下沉到持久化层**（REQ-06 未实现） |

**数据出境是最大合规风险**：工业数据通过 LLM 请求发往境外 API（GPT/Claude）可能违反数据安全法第 36 条。ModelSwitch 需要提供"数据脱敏前置 + 国产模型优先"策略才能缓解。

### 4.4 OPC UA Security 预留

**评分：0 / 10**

| 要求 | 状态 |
|------|------|
| X.509 证书管理 | **完全缺失**——`grep "rcgen\|x509"` 仅命中 LDAP 证书与 TLS 层，无 OPC UA 设备证书管理 |
| 消息加密通道 | **完全缺失**——无 Basic128Rsa15 / Basic256 / Basic256Sha256 安全策略实现 |
| 设备认证体系 | **完全缺失**——无 OPC UA Session/UserIdentityToken 实现 |
| OPC UA 协议栈 | **完全缺失**——`opcua` crate 未在 `Cargo.toml` 中（REQ-01 未启动） |

这是 OPC 场景的**最大能力黑洞**：ModelSwitch 当前对 OPC UA Security 的预留度为 0。`docs/OPC-场景需求调研报告.md` 已明确这是 P0 级差距（REQ-11），需引入 `opcua` crate + rustls + 证书管理体系。

### 4.5 合规维度打分

(2.5 + 3.5 + 2.5 + 0) / 4 = **2.875 ≈ 3.0 / 10**。

| P0-2 | OPC UA Security（X.509/消息签名/安全策略）零实现 | 合规 | 无法满足 IEC 62443 SL2 设备认证要求 |

| P0-4 | 多租户数据隔离仅停留在路由层，未下沉到 storage | 合规 | 跨租户数据混存，违反数据安全法与合同隔离义务 |

### P1（规模化运营前必修）

| # | 问题 | 维度 | 影响 |
|---|------|------|------|
| P1-1 | 内存占用 512MB vs PRD 目标 50MB（10 倍差距） | 运维 | 工控机资源受限场景下密度低；PRD NFR-05 目标需修正 |
| P1-2 | Prometheus 未暴露 `process_resident_memory_bytes` | 运维 | 无法基于内存告警；OOM 风险不可观测 |
| P1-3 | 告警规则仅 3 条，缺磁盘/内存/上游不可达/预算预警 | 运维 | 一人公司无法 7×24 盯仪表盘，告警覆盖度不足 |
| P1-4 | 无微信/钉钉/企业微信通知（REQ-17） | UX/运维 | 工业现场通知偏好不匹配 |
| P1-5 | 数据分类分级能力为 0 | 合规 | 数据安全法第 21 条要求分类分级，当前无元数据标注 |
| P1-6 | LLM 请求将工业数据发往境外 API，无出境管控 | 合规 | 数据安全法第 36 条出境限制风险 |
| P1-7 | 审计日志无工业字段（设备/点位/指令类型） | 合规 | REQ-15 要求未实现，无法支撑工控审计 |
| P1-8 | 无移动端适配（< 768px 核心面板不可用） | UX | REQ-09 要求 ≥ 375px 友好，当前不满足 |
| P1-9 | 前端测试覆盖率 ~22%（目标 80%） | UX | 回归风险高，一人公司无法承受手动回归 |
| P1-10 | 无 onboarding 向导（仅空状态 CTA） | UX | 新用户首次部署摩擦大 |

## 6 一人公司运维工作量估算

基于 ModelSwitch 当前运维负担与 OPC 一人公司典型规模（3-5 家 retainer 客户、每家 200-2000 数据点），估算如下：

### 6.1 部署期（一次性，每客户）

| 任务 | 耗时 | 频次 |
|------|------|------|
| Docker/systemd 部署 + config.toml 配置 | 1-2 小时 | 每客户 1 次 |

| 渠道配置 + 虚拟密钥发放 | 1-2 小时 | 每客户 1 次 |

| 处理客户配额/预算调整请求 | 15 分钟 | 每周 2-3 次 | 30-45 分钟 |

### 6.3 月度运维（每月）

|------|------|
| 灾备演练（备份恢复测试） | 1-2 小时 |

## 7 结论与建议

### 7.1 当前定位

ModelSwitch 作为 **LLM 智能网关**的前端与运维体系已达到**一人公司可交付**的成熟度（UX 6.4 + 运维 6.8）。P0 修复（6/6 完成）显著提升了 UI/运行时一致性，消除了"功能欺骗"类的信任侵蚀。

### 7.2 向 OPC 延伸的关键瓶颈

合规维度（3.0/10）是延伸到 OPC 场景的最大短板：
1. **OPC UA 协议栈与 Security 完全缺位**（REQ-01、REQ-11）——这是准入门槛，不是优化项。
2. **审计日志持久化与字段扩展**——1000 条缓冲必须改为持久化查询；工业字段必须补充。
3. **多租户隔离下沉到 storage 层**——当前仅路由层隔离，合规风险高。

### 7.3 优先行动建议

**短期（1-2 sprint）**：
- 审计日志改为基于 NDJSON 文件的分页查询（消除 1000 条硬上限）
- 补充 Prometheus 内存/磁盘/上游不可达告警规则
- 移动端核心面板（Dashboard/渠道列表/告警）适配到 ≥ 375px
- 前端测试覆盖率提升到 50%（离 80% 目标先走一半）

**中期（3-6 sprint）**：
- 引入 `opcua` crate 作为独立模块（REQ-01）
- 审计日志扩展工业字段（REQ-15）
- 多租户 tenant_id 下沉到 storage（REQ-06）
- OPC UA Security 策略实现（REQ-11）

**长期**：
- 数据分类分级元数据框架
- 等保三权分立角色模型
- 移动端完整适配
