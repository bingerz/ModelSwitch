## 执行摘要

本报告面向工业自动化领域的"一人公司"（OPC = One Person Company，同时与 OPC UA 技术栈高度耦合）这一独特业态，系统梳理其业务全貌、核心痛点、合规约束、技术栈选型与 AI 渗透机会，并将之转化为 18 条可执行的产品需求，作为 ModelSwitch 向 OPC 场景延伸的决策基线。

**核心结论**：

1. **OPC 一人公司是 AI 网关的天然客户**。该业态以一人之力承接工业数据采集（OPC UA/DA）、SCADA/HMI 部署、运维托管等业务，最高频困境是"7×24 监控悖论"——单人无法承担多站点全天候值守。异步告警管道 + LLM 智能分析是破解该悖论的现实路径，与 ModelSwitch 的"AI 网关 + MCP 工具注入"核心能力高度契合。
2. **ModelSwitch 当前 OPC 场景覆盖率约 40%**。可直接复用的能力包括：多模型调度 + MCP 工具注入（智能告警分析）、虚拟密钥 + 预算体系（多客户配额）、审计日志（合规基础）、配置热重载（不停机更新）、熔断状态机（告警规则引擎参考实现）。完全缺失的是 OPC UA 协议栈、时序数据存储、规则/告警引擎、设备数据模型、控制指令管道、实时数据流（MQTT/WebSocket）。
3. **推荐架构路径**：不把 ModelSwitch 改造成 SCADA。保持"AI 分析平面"定位，新建 `opcua-bridge` 数据平面模块，通过 Tokio broadcast channel 解耦。两平面独立演进，避免功能蔓延。
4. **18 条需求中，P0 共 6 条（业务准入门槛）、P1 共 8 条（规模化运营前提）、P2 共 4 条（差异化竞争力）**。最关键的 P0 是 OPC UA 客户端订阅、时序数据存储、规则引擎、告警智能分级、多客户隔离、合规审计。详见第 6 章。

**核心风险**：法律/责任风险（工控安全事件损失可能远超合同金额）、人力瓶颈（单人无法 7×24 响应）、供应商锁定（Kepware 等）与 AI 信任边界（LLM 幻觉）。

## 第 1 章 业务场景全貌

### 1.1 典型业务模式

工业自动化领域的"一人公司"普遍承接以下六类业务，按市场出现频率降序排列：

| 业务类型 | 内涵 | 典型合同周期 | 合同区间（人民币） |
|---------|------|-------------|------------------|
| 系统集成与数据采集 | 将异构 PLC、传感器、仪表通过 OPC UA/DA 汇聚到 SCADA/MES/云端，是 OPC 一人公司最高频的业务类型 | 1-6 个月 | 8-80 万 |
| SCADA/HMI 开发部署 | 基于 Ignition、WinCC、组态王等平台开发监控画面与报警逻辑 | 2 周-3 个月 | 3-30 万 |
| PLC 编程与现场调试 | 承接 Siemens、Allen-Bradley、三菱、汇川等品牌的逻辑编程与现场调试 | 2 周-2 个月 | 3-20 万 |
| 运维外包与远程监控 | 7×24 设备监控、故障响应、报表生成等托管服务 | 持续 retainer | 月 5,000-30,000 元 |
| 协议转换与网关开发 | 在不同品牌设备间做协议适配（Modbus、EtherNet/IP、Profinet、OPC UA 等） | 2-8 周 | 5-30 万 |
| 预测性维护咨询 | 基于采集的设备数据构建分析模型 | 1-3 个月 | 10-50 万 |

OPC UA 已成为工业 4.0 的核心通信标准（IEC 62541），被纳入 RAMI 4.0 参考架构，是上述业务的统一数据层。

### 1.2 客户行业分布

| 行业大类 | 典型细分 | 设备点数规模 |
|---------|---------|-------------|
| 离散制造业 | 机加工、包装、食品加工 | 50-2,000 点 |
| 能源 | 光伏、风电、水务 | 500-5,000 点 |
| 油气 | 上游/下游工艺监测 | 1,000-5,000 点 |
| 楼宇自控 | 暖通、配电、安防 | 200-2,000 点 |

### 1.3 端到端业务流程

一人公司的标准交付链路：

```
需求勘测 → 方案设计 → 设备选型/采购 → PLC 编程/HMI 开发
  → OPC Server 配置 → 网络与安全部署 → 联调测试 → 验收交付
  → 运维托管（retainer 持续服务）
```

其中**运维托管阶段**是 AI/LLM 价值最高的环节：远程运维架构通常为"VPN/网关层 → 数据汇聚层（IIoT 平台）→ 监控告警层（Node-RED / 轻量 SCADA → 微信/钉钉推送）"，数据采集与报表路径为"OPC Server → 时序数据库（InfluxDB / PostgreSQL）→ 报表工具（Grafana / Metabase）"。一人公司通常用 Node-RED 做中间编排。ModelSwitch 在此链路中最自然的卡位是"AI 分析平面"，替代或增强 Node-RED 的告警分级与报表自动化能力。

## 第 2 章 核心痛点深度分析

### 2.1 痛点 1：7×24 监控悖论（人力瓶颈）

**量化描述**：单个工程师每日有效注意力上限约 8-10 小时；而工业现场的故障分布是 24 小时随机的。一人公司若承接 3-8 家 retainer 客户，理论上需要 2.4-6.4 倍的人力才能覆盖全天值守。现实策略三条：(a) 异步告警管道替代主动巡检；(b) 严格限定 retainer 客户数量上限为 3-8 家；(c) 利用 AI/LLM 做告警分级与初步诊断，将工程师从"被动响应"中解放出来专注于高价值处置。**该痛点是 ModelSwitch AI 网关最直接的价值锚点。**

### 2.2 痛点 2：工具链碎片化

**量化描述**：单个 OPC 一人公司需熟悉 3-5 种 PLC 协议（Modbus RTU/TCP、Profinet、EtherNet/IP、OPC UA DA/HA、MQTT Sparkplug B）、2-3 种 SCADA 平台（Ignition / WinCC / 组态王）、3-5 种 OPC Server（KEPServerEX / Matrikon / Software Toolbox TOP Server / Ignition 内置）。每个客户的工具组合各异，导致工程师切换成本高、复用率低。

**直接影响**：现场调试占工时 30-50%；新客户上手周期 2-4 周；同一工程师最多并行承接 2-3 个项目。

### 2.3 痛点 3：合规与责任风险

**量化描述**：工控安全事件造成的停产损失通常以"万元/小时"计量，单次事件直接损失可能远超合同金额（典型合同 3-80 万元 vs. 单日停产损失可达 10-100 万元）。一人公司通常缺乏完善的网络安全保险（年保费 2-10 万，单人公司难承担）和专业法律支持，一旦卷入工控安全事件可能直接面临破产。

**强制合规要求**：IEC 62443 工控网络安全框架、GB/T 22239-2019（等保 2.0 含工控扩展）、数据安全法、个人信息保护法。详见第 3 章。

### 2.4 痛点 4：成本压力

**量化描述**：工业软件授权是一人公司的最大刚性支出：

| 类别 | 主流方案 | 授权区间 |
|------|---------|---------|
| OPC Server | KEPServerEX | $5K-$30K |
| SCADA 平台 | Ignition（无限点数） | 起步约 $3K（对一人公司最友好） |
| 云平台 | AWS SiteWise / Azure IoT / 阿里云工业互联网 | $500-$5K/月 |
| 高端 IoT 平台 | PTC ThingWorx | $50K+/年（门槛过高，一人公司基本不选） |

**对策**：一人公司的核心技术栈逻辑是"**最低授权成本 + 最大复用**"。Ignition + Node-RED + Grafana + InfluxDB 是欧美小集成商的事实标准组合。ModelSwitch 作为 AI 网关，可在此组合中以"轻量增值层"形态存在，而非替代 SCADA。

## 第 3 章 合规要求矩阵

### 3.1 通用合规框架适用性

| 标准/法规 | 适用范围 | 对一人公司的强制等级 | 关键控制点 |
|----------|---------|-------------------|-----------|
| **IEC 62443** | 工业控制系统网络安全 | 强烈推荐（部分行业强制） | SL1-SL4 四级；IEC 62443-2-4 针对集成商认证。一人公司至少需了解 SL2 级控制措施（分区、设备认证、加密、审计） |
| **GB/T 22239-2019（等保 2.0）** | 中国境内工控系统 | 强制（按系统等级） | 工控扩展包：安全管理中心、通信完整性、入侵防范。涉及电力、水务等关键基础设施的项目必须做等保备案 |
| **GB/T 33009** | 工控系统信息安全防护 | 推荐 | 面向系统集成商的实施指南 |
| **数据安全法** | 工业数据分类分级 | 强制 | 重要数据风险评估、全生命周期管理。工业生产数据通常归为"一般数据"或"重要数据"，跨境传输受限 |
| **个人信息保护法** | 涉及人员的数据 | 强制 | 工业场景主要触及运维人员定位、考勤等 |
| **工业和信息化领域数据安全合规指引** | 工信领域 | 强制 | 数据分类分级、风险监测、应急处置 |

### 3.2 行业特定合规

| 行业 | 特定要求 |
|------|---------|
| 电力 | 国网标准（如 Q/GDW 系列）；二次系统安全防护规定 |
| 油气 | HSE 管理体系；防爆认证 |
| 食品 | HACCP 食品安全；批次追溯 |
| 医药 | GMP；数据完整性（ALCOA+） |

### 3.3 合规对产品的硬约束

合规要求直接转化为产品需求：
- 所有操作必须可审计、可追溯（驱动审计日志需求 → 见 REQ-15）
- 工业数据原则上不允许跨境传输（驱动本地化部署、国内云优先 → 见 REQ-09）
- 控制指令必须强制二次确认（驱动安全控制管道 → 见 REQ-08）
- 多客户数据必须严格隔离（驱动多租户强化 → 见 REQ-06）

## 第 4 章 技术栈选型分析

### 4.1 主流 OPC Server 对比

| 方案 | 授权成本 | 点数限制 | 适配性 | 对一人公司的评价 |
|------|---------|---------|--------|----------------|
| KEPServerEX | $5K-$30K | 按授权 | 极广（覆盖 150+ 设备协议） | 行业标杆但贵；Kepware 被 TPG 收购后路线图不确定 |

| **Ignition** | **起步约 $3K** | **无限点数** | **广** | **欧美小集成商事实标准，对一人公司最友好** |
| 开源方案（OpenPLC / ScadaBR） | 0 | 无 | 窄 | 适合学习与小规模试验 |

### 4.2 云平台对比

| 方案 | 月费 | 工业模型支持 | 国内可用性 |
|------|------|-------------|-----------|
| AWS SiteWise | $500-$5K | ISA-95 | 跨境合规风险 |
| Azure IoT | $500-$3K | 设备孪生 | 跨境合规风险 |
| 阿里云工业互联网 | 中 | 行业模型 | 强（国内业务首选） |
| 华为云 IoT | 中 | 设备影子 | 强 |
| PTC ThingWorx | $50K+/年 | 全面 | 门槛过高 |

### 4.3 一人公司推荐选型

**最低成本最优组合**：Ignition（SCADA + OPC UA）+ Node-RED（编排）+ Grafana（可视化）+ InfluxDB（时序数据库）+ ModelSwitch（AI 分析平面）。该组合年度总授权成本 < $5K，远低于全栈商用方案。

**ModelSwitch 在此组合中的定位**：不替代任何工业软件，作为轻量 AI 网关接入 OPC UA 数据流，提供告警智能分级、报表自动生成、RAG 知识库三大增值能力。详见第 5 章与第 8 章。

## 第 5 章 AI/LLM 机会地图

### 5.1 行业趋势

OPC Foundation 已正式启动"AI 时代"计划，将 430+ 行业信息模型（OPC UA Companion Specification）转化为 AI 可用资产。西门子、微软已推出基于 LLM 的工业副驾驶。学术界提出 AAS（资产管理壳）- OPC UA - LLM 架构。**LLM 在工业场景从"实验"走向"产品化"的窗口期正在打开。**

### 5.2 机会矩阵

按"价值 × 实现难度 × ModelSwitch 适配度"三维评估，得到下表（H=高，M=中，L=低）：

| # | AI 场景 | 业务价值 | 实现难度 | ModelSwitch 适配度 | 推荐优先级 |
|---|---------|---------|---------|------------------|-----------|
| 1 | 告警智能分级与根因建议 | H | L | H（MCP 工具注入是杀手锏） | **P0** |
| 2 | 运维报表自动生成 | H | L | H（已有报表框架） | **P0** |
| 3 | 现场知识库 / RAG 副驾驶 | H | M | H（Embeddings + LLM 网关） | **P0** |
| 4 | 投标/技术方案撰写 | M-H | L | M | P1 |
| 5 | 多供应商协议转换辅助 | M | M | M | P1 |
| 6 | 客户沟通/工单总结 | M | L | M | P1 |
| 7 | 工艺优化建议 | H | H | M | P2 |
| 8 | 预测性维护建模辅助 | H | H | L | P2 |

### 5.3 切入环节建议

**最现实的切入环节是场景 1、2、3**（告警分级、报表自动化、RAG 知识库）——投入小、价值直观、不涉及安全关键决策。ModelSwitch 的 MCP 自动注入循环（最多 5 轮）+ 多模型 fallback 天然适配此场景：告警上下文作为 prompt，OPC 工具作为 MCP server，可闭环"AI 分析告警 → 调用工具查询 → 生成建议"。

### 5.4 信任边界

LLM 幻觉是工业场景的红线。原则：**只在低风险环节用 LLM；关键决策保留人工确认**。控制指令下发、安全连锁、批次配方等场景禁止 LLM 直接决策；仅用于解读、建议、报表生成。

## 第 6 章 核心需求清单

> **优先级定义**
> - **P0**：没有它就不能开展 OPC 业务（业务准入门槛）
> - **P1**：有了它才能规模化运营（重要能力）
> - **P2**：锦上添花的增强能力（差异化竞争力）

### REQ-01 OPC UA 客户端订阅

| 字段 | 内容 |
|------|------|
| 优先级 | **P0** |
| 痛点来源 | 工具链碎片化、数据采集是一切业务的入口 |
| 描述 | ModelSwitch 引入 OPC UA 客户端能力，支持连接 OPC UA Server、建立会话、创建订阅与 Monitored Item，将数据点变更事件接入应用内部事件总线 |
| 实现要点 | 引入 `opcua` crate（locka99/opcua，纯 Rust + Tokio，与现有依赖零冲突）作为独立模块，不侵入 LLM 网关 |
| 验收标准 | 1）可连接标准 OPC UA Server（如 Ignition、KEPServerEX）并完成 X.509 证书认证；2）支持配置订阅 1,000+ Monitored Item；3）数据点变更通过 Tokio broadcast channel 推送；4）连接异常自动重连，重连后订阅自动恢复；5）支持订阅配置（采样间隔、队列大小、死区）通过 TOML 热重载 |

### REQ-02 时序数据持久化层

| 字段 | 内容 |
|------|------|
| 优先级 | **P0** |
| 痛点来源 | 历史趋势、报表、告警回溯、合规存档都依赖持久化；当前仅 JSON 文件存储 |
| 描述 | 新增 `storage/` 模块，抽象 `TimeSeriesStore` trait，默认实现用 SQLite + WAL 模式（不引入额外服务依赖） |
| 实现要点 | 用 `sqlx` + SQLite；数据点表结构：`tenant_id, tag_id, timestamp_ns, value, quality`；按 tag_id + 时间分区索引 |
| 验收标准 | 1）支持写入 1,000 点/秒持续 24 小时不丢数据；2）按 tag_id + 时间范围查询 100 万点 P99 延迟 < 200ms；3）单库容量 ≥ 10 GB；4）支持数据保留策略（按时间或容量滚动删除）；5）进程崩溃后数据零丢失（WAL） |

### REQ-03 规则与告警引擎

| 字段 | 内容 |
|------|------|
| 优先级 | **P0** |
| 痛点来源 | 7×24 监控悖论；现有熔断器是固定策略无法表达工业告警规则 |
| 描述 | 新增 `rules/` 模块，定义 `Rule { condition, action, window, cooldown }`。规则求值挂到数据点更新事件，触发时复用现有 `notification/`（Webhook + SMTP） |
| 实现要点 | 用 `expr` crate 或 `cel-interpreter` 构建轻量表达式引擎；不引入 BPMN 重型框架 |
| 验收标准 | 1）支持阈值规则（如 `temp > 80`）、时间窗口规则（如 `持续 30 秒 > 80`）、复合规则（A 与 B 同时满足）；2）支持告警抑制（同规则 N 分钟内只触发一次）；3）支持告警分级（INFO/WARN/CRITICAL）；4）触发后调用 Webhook 或 SMTP 通知；5）规则配置支持 TOML 热重载 |

### REQ-04 告警智能分级（LLM 分析平面）

| 字段 | 内容 |
|------|------|
| 优先级 | **P0** |
| 痛点来源 | 7×24 监控悖论；告警风暴下人工筛选不可行 |
| 描述 | 将告警上下文（点位、值、历史趋势、相关 SOP）作为 prompt，通过 ModelSwitch 多模型调度调用 LLM 生成根因建议与处置优先级。OPC UA 查询能力作为 MCP 工具暴露给 LLM，实现"AI 分析 → 调用工具查证 → 生成建议"闭环 |
| 实现要点 | 复用 ModelSwitch MCP 自动注入循环（最多 5 轮）+ 多模型 fallback。OPC UA 查询封装为 MCP Server（Node.js / Python） |
| 验收标准 | 1）告警触发后 30 秒内生成 AI 分析建议；2）建议包含"根因推测 + 处置建议 + 置信度"；3）AI 分析结果写入审计日志；4）当所有 LLM 渠道熔断时降级为只发原始告警，不阻塞主链路；5）支持按客户/站点配置是否启用 AI 分析 |

### REQ-05 设备与点位数据模型

| 字段 | 内容 |
|------|------|
| 优先级 | **P0** |
| 痛点来源 | 工具链碎片化；无统一设备模型则无法管理多客户多站点 |
| 描述 | 新增 `device/` 模块，参照 ISA-95 层次（Enterprise → Site → Area → Cell → Unit → Tag）设计数据模型。结构体包括 `Site`、`Device`、`Tag` |
| 验收标准 | 1）支持创建/编辑/删除站点、设备、点位；2）每个 Tag 关联 OPC UA NodeId；3）支持批量导入点位表（CSV）；4）支持点位分组（按设备或区域）；5）点位元数据支持工程单位、量程、报警上下限 |

### REQ-06 多客户/多站点数据隔离

| 字段 | 内容 |
|------|------|
| 优先级 | **P0** |
| 痛点来源 | 一人公司承接 3-8 家 retainer 客户，客户数据混存存在合规与责任风险 |
| 描述 | 在 `storage/` 层引入 `tenant_id` 字段，所有查询带租户过滤。虚拟密钥的 `group` 字段天然映射为 `tenant_id`。数据隔离从"请求路由级"下沉到"数据持久化级" |
| 实现要点 | 复用 ModelSwitch `virtual_key/key.rs` 的 group + `channel.account_group` 路由过滤；扩展到 storage 层 |
| 验收标准 | 1）每个客户/站点有独立 `tenant_id`；2）任何数据查询 API 必须带 tenant_id 过滤；3）跨租户访问返回 403；4）虚拟密钥按租户隔离配额；5）审计日志按租户可独立导出 |

### REQ-07 实时数据流通道（WebSocket）

| 字段 | 内容 |
|------|------|
| 优先级 | **P0** |
| 痛点来源 | 现场仪表盘与远程监控需要实时数据推送；SSE 单向且不适合双向通信 |
| 描述 | 在 Axum 路由新增 `/ws` WebSocket 端点（`axum 0.8` 已启用 `ws` feature）。数据流复用 Tokio broadcast channel，订阅 OPC UA 数据点变更后实时推送给前端 |
| 验收标准 | 1）前端通过 WebSocket 订阅指定 Tag，1 秒内开始接收数据；2）单连接可订阅 ≥ 100 个 Tag；3）支持订阅过滤（按 tag、按变化阈值）；4）断线自动重连；5）服务端支持 ≥ 50 并发连接 |

### REQ-08 控制指令安全管道

| 字段 | 内容 |
|------|------|
| 优先级 | **P1** |
| 痛点来源 | 远程运维需要下发控制指令（启停、参数设定），但涉及功能安全 |
| 描述 | 新增 `control/` 模块，强制走"申请 → 审批 → 执行 → 审计"四步流程。复用现有 RBAC + 审计日志。**LLM 不允许直接下发控制指令** |
| 实现要点 | 通过 OPC UA Method Call 或 Write Service 实现。审批环节支持双人确认（操作人 + 批准人） |
| 验收标准 | 1）所有控制指令必须先创建申请单；2）申请单必须经审批才能执行；3）执行结果（成功/失败/超时）写入审计日志；4）高危指令（如停机）强制双人确认；5）指令执行支持超时与回滚（如支持） |

### REQ-09 工业级监控仪表盘

| 字段 | 内容 |

| 验收标准 | 1）支持设备拓扑图展示 ISA-95 层次结构；2）支持实时曲线（刷新间隔 ≤ 1 秒）；3）支持告警列表（按时间/级别排序，可确认/关闭）；4）支持按租户切换视图；5）移动端浏览器友好（≥ 375px 宽度可用） |

### REQ-10 边缘离线运行与数据缓冲

### REQ-11 工业安全合规（OPC UA Security）

|------|------|

### 8.3 架构演进路径

**推荐：双平面解耦架构**

```
┌──────────────────────────────────────────────────┐
│           AI 分析平面（ModelSwitch 现有）          │
│  多 LLM 调度 + MCP 工具注入 + 虚拟密钥 + 审计     │
└──────────────────┬───────────────────────────────┘
                   │ Tokio broadcast channel
┌──────────────────┴───────────────────────────────┐
│         数据平面（新建 opcua-bridge 模块）         │
│  OPC UA 客户端 + 时序存储 + 规则引擎 + 通知       │
└──────────────────────────────────────────────────┘
```

**关键原则**：
1. 不把 ModelSwitch 改造成 SCADA——保持"AI 网关"定位
2. 数据平面独立演进，通过 Tokio channel 或 Redis pub/sub 解耦
3. Axum + Tokio 完全可承载 OPC UA 长连接（`opcua` crate 与现有依赖零摩擦）
4. `spawn_bg()`（`lib.rs:49-93`）已提供带 panic 防护的后台任务封装，可直接用于 OPC UA 会话保活

## 第 9 章 核心诉求总结

OPC 一人公司对 ModelSwitch 的核心诉求可归纳为三大约束，所有需求与设计决策必须在此约束下权衡：

### 9.1 轻量化运营

**定义**：单工程师可承担的运维负担上限。具体指标：
- 部署：单二进制 + SQLite，无外部服务依赖（Redis/Kafka/InfluxDB 都不允许强制依赖）
- 内存：生产负载下 < 200MB（工业工控机内存有限）
- 配置：TOML 文件 + 热重载，零停机
- 监控：开箱即用的 Prometheus metrics，不需要额外配置

**约束**：禁止引入需要专职运维的组件（如 Kafka、Elasticsearch）。`opcua` crate 与 SQLite 都满足这一约束。

### 9.2 合规管控

**定义**：满足工业强制合规要求的最小可行能力集。具体指标：
- 审计：所有控制操作、AI 决策、配置变更可追溯
- 隔离：多客户数据严格隔离，可独立导出/删除
- 本地化：数据可完全本地化，不强制跨境
- 安全：OPC UA Security 策略完整支持

**约束**：合规优先于功能丰富度。宁可不做控制指令，也不允许绕过审批直接下发。

### 9.3 成本控制

**定义**：一人公司可承担的工具成本上限。具体指标：
- 软件授权：年度总授权支出 < 5 万元人民币
- AI 调用：单客户月度 LLM 成本可配额（复用虚拟密钥）
- 硬件：单台工控机（4 核 8GB）可承载 ≥ 3 个租户

**约束**：ModelSwitch 自身必须保持"零授权成本"（开源/自研）。AI 调用成本通过阶梯降级（Tier1 免费 → Tier2 廉价 → Tier3 兜底）控制，与 ModelSwitch 现有调度策略完全一致。
